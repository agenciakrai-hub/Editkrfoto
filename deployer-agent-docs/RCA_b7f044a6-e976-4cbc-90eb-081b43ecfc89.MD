# RCA — Lightroom plugin sync returns HTTP 520 (ai-xmp-gen)

## Problem statement
A Lightroom Lua plugin syncing a 500–2000 photo project gets Cloudflare **HTTP 520**. The plugin calls `GET /api/lr/pending` (header `X-LR-Token`) then `POST /api/lr/complete`. Hypothesis from reporter: `/api/lr/pending` returns all pending `lr_jobs` via `to_list(5000)` including full `xmp_content`, OOM-killing the 512Mi pod or timing out → 520.

## Evidence gathered (active run b7f044a6-e976-4cbc-90eb-081b43ecfc89)

### Pod events / restarts (get_pod_events, last 24h)
Both replicas (`...-dp6ks`, `...-s98rf`) repeatedly failed probes around **2026-10-16 18:30–18:37 UTC**:
- `Liveness probe failed: HTTP probe failed with statuscode: 503` (count 19–20 per pod)
- `Readiness probe failed: HTTP probe failed with statuscode: 503` (count 11–12)
- `Readiness probe failed: Get "http://10.14.57.43:8080/health": EOF`
- `Killing ... Container failed liveness probe, will be restarted`
- `restart_count = 2` on both pods; `last_termination = {reason: "Completed", exit_code: 0}`

**No `OOMKilled` and no exit 137 was observed.** The kill mechanism is **liveness-probe failure (503 / connection EOF) → kubelet restart**, with graceful SIGTERM shutdown (exit 0).

- No tracebacks/MemoryError lines surfaced in the window (crash signal would be absent for a probe-kill SIGTERM).

## Root cause (confirmed mechanism)
`GET /api/lr/pending` returns **all** of a user's pending `lr_jobs` in one JSON response **including the full `xmp_content` of every job** (`to_list(5000)`). During the sync, this user had on the order of ~1000+ pending jobs each carrying a multi-KB-to-tens-of-KB XMP, so the endpoint had to buffer/serialize roughly **tens of MB of JSON in memory on a single-worker uvicorn**. That request **monopolizes the one worker and spikes memory**, the `/health` liveness/readiness endpoint stops responding (503 / connection EOF), Kubernetes **kills and restarts the pod**, and the in-flight plugin connection is severed → the origin resets the connection → **Cloudflare returns 520**.

## Confirmed vs. inferred
- CONFIRMED: repeated liveness/readiness 503 probe failures → pod restarts on both replicas during the sync window; single-worker uvicorn; `lr_jobs` all belong to one user; `xmp_content` values large enough to exceed the DB read cap; endpoint responsive once backlog is 0.
- INFERRED / NOT CONFIRMED: an actual **OOMKill was NOT observed** (no exit 137 / OOMKilled event — termination was a graceful exit 0 from the probe-kill). Memory pressure is a plausible contributor to the unresponsiveness but is **unverified**; the proven kill path is probe-failure-driven restart. Exact XMP avg/max size and the exact pending count at incident time could not be measured (backlog already drained; no aggregation tool).
- NOT REPRODUCED in a sandbox: this is load + production-data dependent and needs the live DB (no secrets/DB in the eph pod), so no sandbox repro was attempted.

## Suggested fixes
1. **Code (E1) — primary, root cause.** Redesign `GET /api/lr/pending` so it never returns the whole backlog with full `xmp_content` in one response:
   - Paginate / batch (e.g. `limit` 50–100 per call with a cursor or `skip`, or a `since`/`after_id` token); drop the `to_list(5000)`.
   - Exclude `xmp_content` from the list payload — return only job ids + light metadata, and have the plugin fetch/write XMP per item (or in small batches) through the `/complete` flow. Stream or chunk rather than buffering all docs.
   - This keeps each HTTP response small and the single worker responsive, which eliminates the probe-kill → 520 path.
2. **User — immediate.** The backlog is currently 0 pending, so a fresh sync should succeed now. If the full project is re-queued, the fix above is required to avoid recurrence at 500–2000 photos.

NOTE: Do not report the app as down — it is currently live and healthy (`/api/lr/pending` returns 401 in ~0.5s). The incident is specific to large-backlog sync requests.
