# RCA — Production Google login bounces owner back to landing (ai-xmp-gen)

**Deployment:** ai-xmp-gen · active run `071ef27d-e921-457e-8bd1-f7c8994fffaf` · template farm (fastapi_react_mongo_shadcn) · frontend_type=cloudflare
**Live origins:** https://ai-xmp-gen.emergent.host (platform) + https://editflow.krfoto.com (custom domain, verified)

## Verdict (root cause)
Cross-origin, credentialed auth requests are **blocked by the browser** because the backend disables CORS credentials whenever `CORS_ORIGINS` is a wildcard.

- `server.py:2239-2245`:
  ```py
  _cors_origins = [o for o in os.environ.get('CORS_ORIGINS','*').split(',') if o]
  _cors_wildcard = '*' in _cors_origins
  app.add_middleware(CORSMiddleware,
      allow_credentials=not _cors_wildcard,   # '*' => allow_credentials=False
      allow_origins=_cors_origins, ...)
  ```
- Production **CORS_ORIGINS = `*`** (confirmed via secret metadata) ⇒ `allow_credentials=False` ⇒ responses omit `Access-Control-Allow-Credentials: true`.
- The frontend calls the API with axios `withCredentials:true` (cookie auth). For a **credentialed cross-origin** request the browser requires `Access-Control-Allow-Credentials: true` on BOTH the preflight and the response. It's missing, so the browser **aborts the request after preflight**.

### Why it only bites the owner / only in prod
`REACT_APP_BACKEND_URL` (baked into the prod build) = **https://editflow.krfoto.com** (the custom domain), NOT the `.emergent.host` origin.
- User on **https://editflow.krfoto.com** → API is **same-origin** → CORS never applies → cookie flows → login works. (This is what the healthy log lines are.)
- Owner on **https://ai-xmp-gen.emergent.host** → every `/api/*` call is **cross-origin** to editflow.krfoto.com → credentials disabled → auth POST blocked → cookie never set → AuthContext `/api/auth/me` finds no session → silent bounce to landing (CORS failures raise no app-level toast).
- **Preview works** because there frontend and backend share one origin (`REACT_APP_BACKEND_URL` == the preview URL) → no cross-origin, CORS not exercised.

### 2. Backend logs around a login attempt (last 24h, active run)
- **Zero** 401/403/500 on auth endpoints. No EMERGENT_AUTH_URL validation exceptions (those would surface as 401 "No se pudo validar la sesión de Google", server.py:344-347).
- Repeated **`OPTIONS /api/auth/session` → 200** (preflight) with **NO matching `POST /api/auth/session`** — the diagnostic signature of a credentialed request the browser refused to send after a preflight lacking `Access-Control-Allow-Credentials`.
- `GET /api/auth/me` → **200** repeatedly = the same-origin (editflow.krfoto.com) users succeeding.

### 3. Set-Cookie / cookie round-trip
- Backend DOES issue it correctly server-side: `session_token`, httponly, **secure=True, samesite="none"**, path=/ (server.py:379-382).
- But on the owner's cross-origin flow the browser never accepts/stores it, because the credentialed POST is blocked by CORS before the response is honored. Even if CORS were fixed, `samesite=none` + a page origin different from the cookie's domain makes it a **third-party cookie**, which Chrome's third-party-cookie restrictions can still drop — so same-origin is the robust state.

### 4. REACT_APP_BACKEND_URL vs site origin
- **REACT_APP_BACKEND_URL = https://editflow.krfoto.com** (confirmed). First-party ONLY when the site is loaded from editflow.krfoto.com. It is cross-site for anyone loading https://ai-xmp-gen.emergent.host.

## Fix options (you apply — I cannot change secrets)
**Preferred (no code change): make the owner log in on the same origin as the API.**
- Have the owner use **https://editflow.krfoto.com** (matches REACT_APP_BACKEND_URL) → same-origin, first-party cookie, no CORS. Login will work immediately.

**If https://ai-xmp-gen.emergent.host must also work:** set an explicit origin allowlist so the code enables credentials — in Deployment → Secrets, set:
```
CORS_ORIGINS = https://editflow.krfoto.com,https://ai-xmp-gen.emergent.host
```
(no `*`). This flips `allow_credentials` to True and echoes the allowed origins with `Access-Control-Allow-Credentials: true`. Save + redeploy. (Cross-domain `samesite=none` third-party-cookie risk still applies for the emergent.host origin; the single-domain approach above avoids it entirely.)

**Separately (not the login bug):** if open registration was intended, ALLOWED_EMAILS should be cleared (empty) — right now only agenciakrai@gmail.com can sign in; all others get 403.
